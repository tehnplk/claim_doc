# fdh-pre-validate: ระบบตรวจสอบ 16 แฟ้ม FDH ก่อนส่งเคลม

skill นี้พาสร้าง web app ที่ให้เจ้าหน้าที่เลือกช่วงวันที่และแฟ้ม แล้วเห็นว่าข้อมูลไหนน่าจะติด C พร้อมวิธีแก้
ตรรกะการตรวจทั้งหมดอยู่ในฐานข้อมูลเป็น view (ไฟล์ใน `sql/`) ตัวแอปมีหน้าที่แค่ตั้งช่วงวันที่ ถาม view และแสดงผล
จึงอย่าเขียนกฎตรวจซ้ำในโค้ดแอป เพราะจะมีกฎสองชุดที่ค่อย ๆ ไม่ตรงกัน

## ไฟล์ใน skill

| ไฟล์ | หน้าที่ |
|---|---|
| `sql/01_views.sql` | ตาราง `fdh_param` (ช่วงวันที่) และ view 18 แฟ้ม `fdh_ins` … `fdh_phdb` |
| `sql/02_c_check.sql` | view `fdh_c_check` รวมกฎตรวจรหัส C คอลัมน์: `c_code, fdh_file, hn, an, seq, found` |
| `references/c_codes.json` | dictionary รหัส C 680 รหัส: `codes["<เลข>"].detail` คือเงื่อนไข, `.fix` คือแนวทางแก้ |
| `scripts/build_views.mjs` | สร้าง `01_views.sql` ใหม่เมื่อ SQL 16 แฟ้มต้นทางเปลี่ยน |

## ขั้นที่ 0: ถามก่อนลงมือ

ก่อนเขียนโค้ดใด ๆ ให้ถามผู้ใช้ว่าจะทำ web app ด้วยอะไร แล้วรอคำตอบ (ถ้า agent มีเครื่องมือถามแบบมีตัวเลือก เช่น AskUserQuestion ให้ใช้ ถ้าไม่มีให้ถามเป็นข้อความ) โดยมีสองตัวเลือกนี้เท่านั้น:

- **Next.js** — หน้าจอและ API อยู่ในโปรเจกต์เดียว (App Router + route handlers, ไลบรารี `mysql2`)
- **Python Flask** — ไฟล์น้อย ติดตั้งง่ายบนเครื่องที่มี Python อยู่แล้ว (`app.py` + template เดียว, ไลบรารี `PyMySQL`)

ต้องถามทุกครั้ง แม้จะเดาได้จากโปรเจกต์ เพราะคนที่ต้องดูแลระบบต่อคือเจ้าหน้าที่ของโรงพยาบาล และเขาเป็นคนรู้ว่าทีมถนัดอะไร
ข้ามคำถามนี้ได้กรณีเดียวคือผู้ใช้ระบุ stack มาในคำสั่งแล้ว

ในรอบเดียวกันให้ถามข้อมูลเชื่อมต่อฐาน HOSxP ที่ยังขาด: host, port, user, ชื่อฐาน
รหัสผ่านให้ผู้ใช้ใส่เองในไฟล์ `.env` ของแอป อย่าขอให้พิมพ์ลงในแชต และให้ `.env` อยู่ใน `.gitignore`

## ขั้นที่ 1: สร้าง view 16 แฟ้ม

ให้แอปมีคำสั่ง setup หนึ่งตัว (`npm run setup-db` หรือ `python setup_db.py`) ที่รัน `sql/01_views.sql` ตามด้วย `sql/02_c_check.sql`
ผ่าน driver ของแอปเอง จะได้ไม่ต้องพึ่ง `mysql` client บนเครื่อง ให้คัดลอกไฟล์ SQL ทั้งสองเข้าโปรเจกต์แอป แล้วแยกคำสั่งด้วย `;` ท้ายบรรทัด
(ในไฟล์ไม่มี `;` กลางคำสั่ง) คำสั่ง setup รันซ้ำได้ ผลเท่าเดิม

setup สร้าง object ใหม่ในฐาน 20 ตัว ชื่อขึ้นต้น `fdh_` ทั้งหมด (ตาราง `fdh_param` 1 ตัว และ view 19 ตัว) ไม่แตะตารางเดิมของ HOSxP
แต่เป็นการเขียนลงฐานของโรงพยาบาล จึงต้องบอกผู้ใช้ว่าจะสร้างอะไร ที่ฐานไหน แล้วรอคำยืนยันก่อนรันครั้งแรกบนฐานนั้น
ถ้ามีฐานทดสอบหรือฐานสำรอง ให้เสนอใช้ฐานนั้นก่อน

ถ้า view ไหนสร้างไม่ผ่านเพราะฐานนั้นไม่มีตารางหรือคอลัมน์ที่ SQL อ้างถึง ให้รายงานชื่อ view กับข้อความ error ตามจริง
อย่าแก้ SQL เองเงียบ ๆ เพราะ mapping ฟิลด์ต่างกันในแต่ละโรงพยาบาล และผู้ใช้ต้องเป็นคนตัดสิน

## ขั้นที่ 2: หน้าจอหลัก

หน้าจอเดียว แบ่งสามส่วน:

```
┌──────────────────────────────────────────────────────────┐
│ ช่วงวันที่: [ start ] ถึง [ end ]  [ตรวจสอบ]              │  ← แถบบนสุด
├──────────────┬───────────────────────────────────────────┤
│ INS      (3) │ แฟ้ม IPD — 412 แถว — พบ 17 เคส ใน 3 รหัส  │
│ PAT     (12) │                                           │
│ OPD          │ รหัส │ เงื่อนไข │ จำนวน │ แนวทางแก้       │
│ ORF          │ C121 │ …        │   9   │ …               │
│ ODX          │                                           │
│ OOP          │ รายเคส: รหัส │ HN │ AN │ SEQ │ ค่าที่พบ   │
│ IPD ◀   (17) │                                           │
│ …            │                                           │
└──────────────┴───────────────────────────────────────────┘
   left tab                 right panel
```

- **แถบบนสุด:** เลือกวันที่เริ่มและสิ้นสุดด้วย `<input type="date">` ค่าเริ่มต้นคือวันแรกของเดือนนี้ถึงวันนี้ เปลี่ยนช่วงแล้วผลทุกส่วนต้องโหลดใหม่
- **Left tab:** รายการแฟ้มเรียงตามลำดับมาตรฐาน คลิกเพื่อเลือก แสดงจำนวนเคสที่พบเป็น badge ข้างชื่อแฟ้ม
  รายการคือ INS, PAT, OPD, ORF, ODX, OOP, IPD, IRF, IDX, IOP, CHT, CHA, AER, ADP, LVD, DRU, LABFU, PHDB
  (ชุด "16 แฟ้ม" ปัจจุบันมี 18 แฟ้ม ให้แสดงครบทั้ง 18)
- **Right panel:** ผล validate ของแฟ้มที่เลือกในช่วงวันที่นั้น ประกอบด้วย
  1. บรรทัดสรุป: จำนวนแถวในแฟ้ม จำนวนเคสที่พบ จำนวนรหัส
  2. ตารางสรุปต่อรหัส: รหัส (แสดงเป็น `C121`), เงื่อนไข (`detail`), จำนวน, แนวทางแก้ (`fix`)
  3. ตารางรายเคส: รหัส, HN, AN, SEQ, ค่าที่พบ คลิกรหัสในตารางสรุปเพื่อกรองรายเคส

สถานะที่ต้องแยกให้ชัดใน right panel เพราะความหมายต่างกันและผู้ใช้จะตัดสินใจส่งเคลมจากตรงนี้:

- แฟ้มมีกฎและไม่พบเคส → "ไม่พบจากกฎที่มี (ตรวจ N รหัส)" ไม่ใช่ "ผ่าน"
- แฟ้มยังไม่มีกฎ → "แฟ้มนี้ยังไม่มีกฎตรวจ" พร้อมจำนวนแถว (ตอนนี้กฎมีเฉพาะ PAT, OPD, IPD, INS)
- แฟ้มว่างในช่วงวันที่นั้น → บอกว่าไม่มีข้อมูล เพื่อไม่ให้เข้าใจว่าตรวจแล้วไม่พบ
- query ล้มเหลว → แสดงข้อความ error ไม่แสดงตารางว่าง

## ขั้นที่ 3: API ฝั่ง server

สอง endpoint พอ:

| Endpoint | คืนค่า |
|---|---|
| `GET /api/summary?start=&end=` | จำนวนเคสต่อแฟ้ม สำหรับ badge ใน left tab: `SELECT fdh_file, COUNT(*) FROM fdh_c_check GROUP BY fdh_file` |
| `GET /api/validate?file=&start=&end=` | `{ file, rows, ruleCodes, summary: [{c_code, detail, fix, n}], cases: [{c_code, hn, an, seq, found}] }` |

view อ่านช่วงวันที่จากตาราง `fdh_param` (MySQL ไม่ยอมให้ view ใช้ตัวแปร `@start_date`) ทุก request จึงต้องทำตามลำดับนี้บน connection เดียว:

```sql
START TRANSACTION;
UPDATE fdh_param SET start_date = ?, end_date = ? WHERE id = 1;
SELECT ... FROM fdh_c_check WHERE fdh_file = ?;   -- และ SELECT COUNT(*) FROM fdh_<แฟ้ม>
ROLLBACK;
```

ต้อง `ROLLBACK` เสมอ (รวมกรณี error) และห้าม `COMMIT` เพราะนี่คือสิ่งที่ทำให้ผู้ใช้สองคนตรวจคนละช่วงวันที่พร้อมกันได้โดยไม่ปนกัน:
ค่าที่ `UPDATE` มองเห็นเฉพาะใน transaction ของตัวเอง ส่วน request ที่ชนกันจะรอคิวที่ row lock

ข้อกำหนดอื่นของ API:

- `file` ต้องเทียบกับรายการ 18 แฟ้มแบบ whitelist ก่อนนำไปประกอบชื่อ view เพราะชื่อ view ใส่เป็น parameter ของ query ไม่ได้ ส่วนวันที่และค่าอื่นให้ส่งเป็น parameter เสมอ
- `start`, `end` ต้องเป็น `YYYY-MM-DD` และ `start <= end` ไม่ผ่านให้ตอบ 400
- `ruleCodes` คือรหัสที่มีกฎสำหรับแฟ้มนั้น อ่านจาก `sql/02_c_check.sql` ตอนเริ่มแอป (บรรทัดที่ขึ้นต้น `SELECT '<เลข>', '<แฟ้ม>'`) เพื่อให้หน้าจอบอกได้ว่า "ตรวจ N รหัส"
- `detail` และ `fix` เติมจาก `references/c_codes.json` ที่โหลดครั้งเดียวตอนเริ่มแอป (คัดลอกไฟล์เข้าโปรเจกต์)
- จำกัด `cases` ที่ 1,000 แถวต่อ request และบอกในผลลัพธ์ถ้าถูกตัด
- ผลตรวจมี HN/AN/เลขบัตรประชาชน ให้แอปฟังเฉพาะ `127.0.0.1` เป็นค่าเริ่มต้น ถ้าผู้ใช้ต้องการเปิดในเครือข่ายโรงพยาบาล ให้ถามเรื่องการ login ก่อน

user ของฐานข้อมูลที่แอปใช้ต้องการสิทธิ์ `SELECT` บนฐาน HOSxP และ `UPDATE` บน `fdh_param` เท่านั้น (สิทธิ์สร้าง view ใช้เฉพาะตอน setup)

## ขั้นที่ 4: ตรวจว่าใช้งานได้จริง

ก่อนบอกผู้ใช้ว่าเสร็จ ให้เปิดแอปจริงแล้วลองทั้งเส้นทาง: เลือกช่วงวันที่ที่มีข้อมูล คลิกแฟ้ม IPD และ PAT ดูว่าตัวเลขใน badge ตรงกับตารางใน right panel
แล้วเทียบจำนวนกับ `SELECT COUNT(*) FROM fdh_c_check WHERE fdh_file = 'IPD'` ที่รันตรงกับฐานในช่วงวันที่เดียวกัน
ถ้าเชื่อมต่อฐานไม่ได้ ให้บอกตรง ๆ ว่ายังไม่ได้ทดสอบกับข้อมูลจริง

## ข้อจำกัดที่ต้องแสดงในหน้าจอ

ใส่ข้อความสั้น ๆ ไว้ท้าย right panel เพื่อไม่ให้ผู้ใช้เข้าใจว่าไม่พบแปลว่าจะไม่ติด C:

- กฎมี 22 รหัสจาก 680 รหัส ครอบคลุมข้อมูลพื้นฐานผู้ป่วยและผู้ป่วยใน
- รหัสที่ต้องเทียบกับฐานของ สปสช. ตรวจจากฝั่งโรงพยาบาลไม่ได้ เช่น C305 (Approve Code ไม่ตรง), C349 (ไม่พบ Authentication), C999 (ไม่พบสิทธิ)
- SQL ต้นทางใส่ค่า default ทับค่าว่าง (เช่น `COALESCE(pt.sex, '1')`, `COALESCE(i.dchstts, '1')`) ทำให้ C103, C111, C112, C160 แทบไม่ขึ้นจาก view แม้ข้อมูลใน HOSxP จะว่างจริง

## เพิ่มกฎใหม่

กฎหนึ่งข้อคือ `SELECT` หนึ่งก้อนใน `sql/02_c_check.sql` ที่คืนแถวที่ผิดเงื่อนไข ต่อกันด้วย `UNION ALL` เพิ่มแล้วรัน setup ใหม่ หน้าจอจะเห็นกฎใหม่เองโดยไม่ต้องแก้โค้ดแอป

1. หาเงื่อนไขของรหัสใน `references/c_codes.json` (ค้นด้วย `"<เลข>": {` อย่าอ่านทั้งไฟล์)
2. เพิ่มก้อน `SELECT '<เลข>', '<แฟ้ม>', hn, an, seq, <ค่าที่พบ> FROM fdh_<แฟ้ม> WHERE <เงื่อนไขที่ผิด>` โดยขึ้นบรรทัดด้วย `SELECT '<เลข>', '<แฟ้ม>'` ตามรูปแบบเดิม
3. ลองกับช่วงวันที่ที่รู้ว่ามีเคสติดรหัสนั้นจริงจาก REP ที่ สปสช. ตอบกลับ เพื่อยืนยันว่ากฎจับได้

เขียน SQL ของกฎด้วย ASCII เท่านั้น ข้อความไทยให้อยู่ใน `c_codes.json` เพราะฐาน HOSxP หลายแห่งเป็น tis620 และ literal ไทยใน view จะชน collation

เมื่อ SQL 16 แฟ้มต้นทางเปลี่ยน ให้สร้าง view ใหม่แล้วรัน setup อีกรอบ:

```
node scripts/build_views.mjs <โฟลเดอร์ที่มี 01_INS.sql … 18_PHDB.sql> sql/01_views.sql
```
