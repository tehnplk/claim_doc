# fdh-submit-claim: ส่งเคลม 16 แฟ้มไปที่ FDH

การส่งเคลมคือการอัปโหลด 16 แฟ้มของ visit ที่ให้บริการแล้วไปที่ FDH ของกระทรวงสาธารณสุข
ขั้นตอนนี้ทำหลังปิดสิทธิ เพราะแฟ้ม INS ช่อง `PERMITNO` ต้องใส่รหัสปิดสิทธิ (`EP…`) ที่ได้จาก สปสช.
FDH เป็นคนละระบบกับ สปสช. และใช้ token คนละตัว

เนื้อหาใน skill นี้ถอดจากโค้ดและคู่มือใน `ganggy/FDHChecker` (`server/fdhExport.ts`, `server/index.ts` และ `knowlage/vault/MOPH_FDH_MANUAL_V3.md`)
ยังไม่มีใครยืนยันกับ API จริงในโปรเจกต์นี้ ถ้า FDH ตอบไม่ตรงกับที่เขียนไว้ ให้เชื่อคำตอบจริงและรายงานผู้ใช้

## สิ่งที่ต้องมีก่อนเริ่ม

ถามผู้ใช้ให้ครบก่อนเขียนโค้ดหรือยิง API:

| ค่า | ความหมาย |
|---|---|
| `baseUrl` | ระบบทดสอบ (UAT) `https://uat-fdh.inet.co.th` หรือระบบจริง (PRD) `https://fdh.moph.go.th` |
| `user` | ชื่อผู้ใช้ MOPH Account ที่มีสิทธิ `MOPH_CLAIM_API` |
| `password` | รหัสผ่านของบัญชีนั้น |
| `hcode` | รหัสหน่วยบริการ 5 หลัก |
| ช่วงวันที่ และ OP หรือ IP | ขอบเขตของ visit ที่จะส่ง |

เริ่มที่ UAT เสมอ เปลี่ยนเป็น PRD เมื่อผู้ใช้สั่งเท่านั้น
ชื่อผู้ใช้และรหัสผ่านให้ผู้ใช้ใส่เองในไฟล์ `.env` อย่าขอให้พิมพ์ลงในแชต และให้ `.env` อยู่ใน `.gitignore`

## ขั้นที่ 1: เตรียม 16 แฟ้ม

ชุดแฟ้ม: INS, PAT, OPD, ORF, ODX, OOP, IPD, IRF, IDX, IOP, CHT, CHA, AER, ADP, LVD, DRU

ถ้าฐานมี view `fdh_ins`, `fdh_pat`, … จาก skill `fdh-pre-validate` อยู่แล้ว ให้ export จาก view เหล่านั้น หนึ่ง view ต่อหนึ่งแฟ้ม
ถ้ายังไม่มี ให้สร้างด้วย skill `fdh-pre-validate` ก่อน อย่าเขียน query 16 แฟ้มขึ้นใหม่
skill นี้ไม่มีโครงสร้างคอลัมน์ของแต่ละแฟ้ม ให้ยึดตาม view

ข้อกำหนดของไฟล์:

- ชื่อไฟล์เป็นชื่อแฟ้มตัวพิมพ์ใหญ่ เช่น `INS.txt`
- คั่นคอลัมน์ด้วย `|` ขึ้นบรรทัดด้วย `\r\n`
- วันที่เป็น `YYYYMMDD` เวลาเป็น `HHMM`
- ไม่เกิน 16 ไฟล์ รวมไม่เกิน 50 MB ต่อครั้ง ถ้าเกินให้แบ่งช่วงวันที่
- ต้องมี INS, PAT, CHT และ OPD หรือ IPD อย่างน้อยหนึ่งแฟ้ม
- แต่ละแฟ้มเชื่อมกันด้วย HN, SEQ และ AN ทุกแฟ้มในชุดต้องมาจาก visit ชุดเดียวกัน
- `INS.PERMITNO` ใส่รหัสปิดสิทธิ (`EP…`)

ก่อนส่งให้นับ visit ที่ `PERMITNO` ยังว่างหรือไม่ขึ้นต้นด้วย `EP` แล้วรายงานผู้ใช้
visit เหล่านั้นยังไม่ปิดสิทธิ ให้ผู้ใช้เลือกว่าจะตัดออกหรือไปปิดสิทธิก่อนด้วย skill `nhso-close-privilege`

ถ้าโปรเจกต์มีระบบตรวจรหัสติด C จาก `fdh-pre-validate` ให้รันตรวจก่อนและแสดงผลให้ผู้ใช้ตัดสินใจ

## ขั้นที่ 2: ขอ token

```
POST {baseUrl}/token?Action=get_moph_access_token&user=<user>&password_hash=<SHA-256>&hospital_code=<hcode>
```

ไม่มี body ส่งค่าทั้งหมดใน query string
`password_hash` คือรหัสผ่านที่แปลงเป็น SHA-256 แบบเลขฐานสิบหก

```bash
FDH_HASH=$(printf '%s' "$FDH_PASSWORD" | sha256sum | cut -d' ' -f1)
curl -X POST "$FDH_BASE_URL/token?Action=get_moph_access_token&user=$FDH_USER&password_hash=$FDH_HASH&hospital_code=$FDH_HCODE"
```

คำตอบคือ token ที่ใช้ในขั้นที่ 3
รหัสผ่านอยู่ใน URL อย่าเขียน URL นี้ลง log และอย่าใส่ในข้อความ error ที่แสดงผู้ใช้
skill นี้ไม่รู้อายุของ token ให้ขอใหม่ทุกครั้งที่ส่ง

## ขั้นที่ 3: อัปโหลด 16 แฟ้ม

```
POST {baseUrl}/api/v2/data_hub/16_files
Authorization: Bearer <token>
Content-Type: multipart/form-data
```

| Path | รูปแบบไฟล์ |
|---|---|
| `/api/v1/data_hub/16_files` | ไม่มีบรรทัดหัวคอลัมน์ |
| `/api/v2/data_hub/16_files` | มีบรรทัดหัวคอลัมน์ (FDHChecker ใช้ตัวนี้) |

ใช้ v2 และใส่บรรทัดหัวคอลัมน์ในทุกไฟล์ ถ้าเลือก v1 ต้องตัดบรรทัดหัวออก อย่าผสมกัน

| ฟิลด์ใน form | ค่า |
|---|---|
| `type` | `txt` หรือ `dbf` |
| `file` | ไฟล์แต่ละแฟ้ม ใส่ฟิลด์ชื่อ `file` ซ้ำตามจำนวนไฟล์ |

payload เป็น form แบบ multipart ไม่ใช่ JSON:

```bash
curl -X POST "$FDH_BASE_URL/api/v2/data_hub/16_files" \
  -H "Authorization: Bearer $FDH_TOKEN" \
  -F "type=txt" \
  -F "file=@INS.txt" \
  -F "file=@PAT.txt" \
  -F "file=@OPD.txt" \
  -F "file=@ODX.txt" \
  -F "file=@CHT.txt" \
  -F "file=@CHA.txt" \
  -F "file=@DRU.txt"
```

ตั้ง timeout ให้คำขอ (FDHChecker ใช้ 120 วินาที)

## ขั้นที่ 4: อ่านคำตอบ

เมื่อ FDH รับไฟล์:

```json
{ "status": 200, "message": "success", "message_th": "บันทึกข้อมูลสำเร็จ" }
```

ถือว่าส่งสำเร็จเมื่อ `status` ใน body เป็น `200` HTTP 200 อย่างเดียวไม่พอ
skill นี้ไม่รู้รูปแบบคำตอบเมื่อส่งไม่สำเร็จ ให้แสดง body ทั้งก้อนที่ FDH ตอบมา

คำตอบนี้แปลว่า FDH รับไฟล์แล้ว ยังไม่ใช่ผลการตรวจเคลม
ผลว่าเคสไหนติด C หรือถูกปฏิเสธจะมากับไฟล์ REP ภายหลัง ให้บอกผู้ใช้ตามนี้ อย่ารายงานว่า "เคลมผ่าน"

คู่มือ FDH มี endpoint ตรวจสถานะหลังส่ง (`/api/v1/data_hub/total_visit`, `/chk/count`, `/chk/detail`) แต่ skill นี้ไม่มีรายละเอียด ถ้าผู้ใช้ต้องการ ให้ขอเอกสารจากผู้ใช้

## ขั้นที่ 5: เก็บประวัติการส่ง

เก็บชุดไฟล์ที่ส่งและคำตอบของ FDH ไว้ในโฟลเดอร์ของรอบนั้น เช่น `fdh_out/<วันที่ส่ง>_<ช่วงวันที่>/` พร้อมจำนวน visit ต่อแฟ้ม
อย่าสร้างหรือแก้ตารางในฐาน HOSxP เพื่อเก็บสถานะการส่ง ถ้าผู้ใช้ต้องการเก็บในฐาน ให้ถามว่าจะใช้ตารางไหน
โฟลเดอร์นี้มีข้อมูลผู้ป่วย ให้อยู่ใน `.gitignore`

## ข้อควรระวัง

- **ส่งระบบจริงแล้วย้อนไม่ได้จาก skill นี้** skill นี้ไม่รู้วิธียกเลิกหรือแก้ชุดที่ส่งแล้ว ก่อนยิงครั้งแรกให้แสดงปลายทาง (UAT หรือ PRD) ช่วงวันที่ และจำนวนแถวต่อแฟ้ม แล้วรอคำยืนยันจากผู้ใช้
- **ลองชุดเล็กก่อน** ส่งช่วงวันที่แคบที่สุดที่ UAT ตรวจคำตอบ แล้วจึงขยาย
- **ส่งซ้ำ** skill นี้ไม่รู้ว่า FDH จัดการชุดที่ส่งซ้ำอย่างไร ถ้าช่วงวันที่ซ้อนกับรอบที่เคยส่งในประวัติ ให้เตือนผู้ใช้ก่อน และถ้าคำขอหมดเวลา อย่าส่งใหม่เอง ให้รายงานผู้ใช้
- **ห้ามปิดการตรวจ TLS** (`verify=False`, `rejectUnauthorized: false`) เพราะ token และข้อมูลผู้ป่วยวิ่งผ่านการเชื่อมต่อนี้
- **log** อย่าพิมพ์ token รหัสผ่าน hash หรือ URL ขอ token ลง log

## ตรวจว่าใช้งานได้จริง

ก่อนบอกผู้ใช้ว่าเสร็จ ให้ยืนยันกับ UAT หนึ่งรอบ:

1. ขอ token ได้
2. อัปโหลดชุดเล็กแล้ว body ตอบ `status: 200`
3. ไฟล์ที่ส่งกับคำตอบถูกเก็บในโฟลเดอร์ประวัติ

ถ้ายังไม่มีบัญชีหรือผู้ใช้ยังไม่อนุญาตให้ยิง ให้บอกตรง ๆ ว่าทดสอบได้แค่การสร้างไฟล์ ยังไม่ได้ทดสอบกับ FDH
